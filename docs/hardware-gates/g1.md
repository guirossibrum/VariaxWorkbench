## 1. What the app reads

Stage 1 reads information the Linux kernel already holds in memory. It lists
one directory, opens plain files for reading and reads link targets; nothing
else. The complete list (`<root>` is `/`; tests use a temporary fake tree):

| Source (read only) | How | Field | Why |
| --- | --- | --- | --- |
| `/sys/bus/usb/devices/` | `read_dir` | entry names (`usb1`, `1-2`, `1-2:1.0`, …) | find devices and interfaces |
| `/sys/bus/usb/devices/<dev>/idVendor`, `idProduct` | `read_to_string` | USB vendor/product from the stored device descriptor | find `0e41:4650` |
| `/sys/bus/usb/devices/<dev>/bcdDevice` | `read_to_string` | device release from the stored device descriptor | report only |
| `/sys/bus/usb/devices/<dev>/product` | `read_to_string` | product string the kernel stored at plug-in | report only |
| `/sys/bus/usb/devices/<dev>:<cfg>.<n>/bInterfaceNumber` | `read_to_string` | interface number from the stored interface descriptor | list interfaces 0 and 1 |
| `/sys/bus/usb/devices/<dev>:<cfg>.<n>/driver` | `read_link` (target name only) | which kernel driver is bound | expect `snd-usb-pod` on 0, `snd-usb-variax` on 1 |
| `/proc/asound/cards` | `read_to_string` | ALSA card numbers, ids and names | report only |

Not read: `serial`, `manufacturer`, `descriptors`, any other attribute,
`/dev/bus/usb/*` (usbfs), `/dev/snd/*`, MIDI ports, audio streams. Nothing is
written to `/sys` or `/proc`. No driver is bound, unbound, detached or
reloaded.

| Read | Kernel code | What it does |

### 3b. Kernel startup traffic (not caused by the app)

When the PODxt Live is plugged in, Linux talks to it before this app runs.
G1 accepts that as normal OS behaviour. All rows below are static readings of
the commit above, never observed live.

| # | Traffic | Driver | Label | Source |
| --- | --- | --- | --- | --- |
| 1 | Standard USB enumeration (descriptor reads, address, configuration, string caching) | USB core | **unverified** (generic USB behaviour; `drivers/usb/core/hub.c` not read) | — |
| 2 | `SET_INTERFACE` interface 0 → altsetting 1 | `snd-usb-pod` via `line6_probe` | verified from source | `driver.c:785–791`; altsetting `pod.c:488–499` (`LINE6_PODXTLIVE_POD`, matched on interface 0, `pod.c:418`) |
| 3 | Interrupt-IN polling of endpoint `0x84` starts and continues while bound | `snd-usb-pod` (`LINE6_CAP_CONTROL`) | verified from source; host reads only | `driver.c:686–719` `line6_init_cap_control` → `driver.c:62–87` `line6_start_listen`; resubmitted `driver.c:331` |
| 4 | After 1000 ms: version request `F0 7E 7F 06 01 F7` on interrupt-OUT endpoint `0x03`, **once** | `snd-usb-pod` startup `POD_STARTUP_VERSIONREQ` | verified from source | `pod.c:397–403`, `pod.c:279–282`; bytes `driver.c:38–40`; send `driver.c:231–248`, endpoint `driver.c:154–170` |
| 5 | Only if a reply starting `F0 7E 7F 06 02` arrives: serial-number read of device address `0x80D0`, 4 bytes, by vendor control transfers: OUT request `0x67`, wValue `0x0421`, wIndex `0x80D0`, no data; then up to 50 IN `0x67` wValue `0x0012` length polls, 2 ms apart; then IN `0x67` wValue `0x0013`, 4 bytes | `snd-usb-pod` `POD_STARTUP_SETUP` | verified from source (what is sent); **unverified** whether the POD treats it as read-only | `pod.c:182–190`, `pod.c:283–285`; `driver.c:468–473` → `driver.c:340–405` |
| 6 | Then the POD sound card is registered (no USB transfer in this step) | `snd-usb-pod` | verified from source | `pod.c:287–290`; source comment `pod.c:391–395` says registering earlier made the unit show "Invalid Code Error 07" |
| 7 | `SET_INTERFACE` interface 1 → altsetting 1; interrupt-IN polling of `0x86` | `snd-usb-variax` via `line6_probe` | verified from source/object code | linux-transport.md, "Property row for interface 1"; `driver.c:785–791`, `driver.c:686–719` |
| 8 | Version request `F0 7E 7F 06 01 F7` on endpoint `0x05`, first after 1000 ms, then **repeated every 1000 ms until a matching reply** | `snd-usb-variax` startup `VARIAX_STARTUP_VERSIONREQ` | verified from source | `variax.c:174–176` (first schedule), `variax.c:89–95` (reschedule, then send) |
| 9 | Activate `F0 00 01 0C 07 00 2A 01 F7`, then the Variax sound card is registered | `snd-usb-variax` states 1–2 | verified from source: reached only after a reply for product `0x00070000`. What this means for G1: with this guitar the stock `snd-usb-variax` driver
keeps sending one version request per second on interface 1 for as long as it
is bound (inferred from rows 8–9; never observed). The POD driver sends one
version request and, if answered, one serial-number read. All of this happens
whether or not the app runs. The app adds none of it.

## 4. Procedure (for the #158 build only)

1. Use the build from #158. Confirm the app's Device check banner says only
   **G1 open**; steps 2–4 must still show as locked.
2. Plug the PODxt Live (Variax attached, powered) into USB. Wait 10 seconds.
3. Start the app, open **Device check…**, read step 1, choose **Yes** for
   step 1 only.
4. When step 1 finishes, choose **No** for step 2. Close the app.
5. Copy the Report text into issue #125.

### Stop conditions

Stop and report if any of these happen: the app offers to run step 2, 3 or 4;
the app asks for a password or permissions; more than one PODxt Live is listed;
the PODxt Live display, lights or sound change when you choose Yes; the app
shows an error. Unplugging the USB cable is always allowed.

### What is recorded

The Report: stage numbers, gate labels, your Yes/No answers, pass/stop, the
USB vendor/product, the bus path (for example `1-2`), interface numbers and
driver names, and the sound card list. No serial number, preset name, file
path or audio. It is saved in #125 as real-hardware evidence, separate from
simulation results.

## 5. G1 authorization record

**How owner authorization works (owner rule, 2026-11-22).** The owner does not
sign forms or comment in GitHub issues to authorize a gate. Authorization is the
owner's direct, explicit permission given to an agent in a working session. The
agent then records the date, the owner's words, the gate and its scope here and
on the gate issue. Each gate needs its own permission. Permission for one gate
never extends to another, and general permission to work on the project is not
gate permission.

**G1 record.** On 2026-11-22 the owner wrote, in a Claude Code session: "i am not
signing the issue - change the rule- I give direct expressed permission - no
signing in the github issues". That permission covers gate G1 only, under the
terms below. The commit of the #158 build that opens the G1 lock is recorded on
#125 when that build is merged.

Terms of the G1 permission, as recorded by the agent from this procedure:

  PODxt Live and Variax 600 that follow section 4, using the build from #158,
  which opens only the G1 lock.
- The app may read the files listed in section 1. It may not send any USB, MIDI
  or audio data, open device nodes, or change drivers.
- Kernel startup traffic in section 3b, including the Variax driver's repeated
  version request and the POD driver's serial-number read, is accepted as normal
  Linux behaviour that happens with or without the app.
- The owner runs the test. Agents do not run the real step 1 themselves.
- This does not authorize G2–G8.
