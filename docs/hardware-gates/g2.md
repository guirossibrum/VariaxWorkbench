## 1. What the local captures establish

`messages.json` record has only `direction` and `message`. There is no
interface number, endpoint, or per-message time. The folder names are the
session clocks. `identity.syx` in the two nonempty folders is the 17-byte
Variax reply, not the request.

| Folder | What the file shows |

| `variax-usb-20261114-235024` | 24 packets. Assembled order: one outbound `F0 7E 7F 06 01 F7`, one inbound reply equal to the published Variax 600 identity (product `0x00070004`, ASCII `0310`), then other SysEx that continues into a settings read. |

## 2. Request, reply, interface, and bounds

Not authorized, and not run. If a future build is allowed to run stage 2,
the only request bytes are `read_session::IDENTITY_REQUEST`:

`F0 7E 7F 06 01 F7`

Sent once. The expected reply is the Variax 600 shape already published in
`src/midi.rs`:

`F0 7E 7F 06 02 00 01 0C 07 00 04 00 30 33 31 30 F7`

Product `0x00070004`, version 3.10. The procedure does not send a second
identity request, `midi_enable`, either settings request, or `MIDI_DISABLE`.
Those belong to gate G3.

The live code path, when a future build is allowed to run it, is
`usb::read_identity`. It checks gate G2 and then stops. It does not call
`read_current`, so it does not also require gate G3. Device check lists stage
2 in `LIVE_STAGES`. `live_stage_available` is still false while G2 is locked,
and it is also false in a binary built without the `usb` feature. Opening
only `G2_IDENTITY_REQUEST_LOCKED` in a build that already includes `usb`
is what makes step 2 available. This round does not call the live function.
The lock returns before USB enumeration.

| Step | Where | Bound |
| --- | --- | --- |
| Find the one `0e41:4650` device | `Session::open_handle` | Stop if the count is not 1. No detach yet |
| If a kernel driver is active on interface 1, detach it | `detach_kernel_driver(1)` | Interface 1 only. A detach failure stops before claim and does not reattach |
| Claim interface 1 | `claim_interface(1)` | If this fails, do not release. Do reattach when detach succeeded |
| Select altsetting 1 | `set_alternate_setting(1, 1)` | If this fails, release because claim succeeded, then reattach |
| Send the 6-byte request on interrupt OUT `0x05` | `write_interrupt`, 16-byte chunks, 1 second timeout, 5 ms between chunks | One request. A cancel before this send does not send |
| Read interrupt IN `0x86` until the same 3 second deadline | 100 ms polls | The first complete reply is kept. Polling continues until the deadline. A second complete reply before that deadline is ambiguous and does not pass |
| Release interface 1 | only when claim succeeded | A release error is kept, and reattach is still attempted |
| Reattach the kernel driver on interface 1 | whenever detach succeeded | Includes claim failure, alternate-setting failure, and cancel before the send |

Choosing No, or closing the window before Yes starts the exchange, sends
nothing and does not detach or reattach. Close in the same moment as Yes
wins, and the exchange does not start. Once Yes has started, this window
cannot cancel the exchange: it runs to the end on the screen, including
giving the driver back. The offline model can still script a cancel after
detach and before the send. That script sends nothing and still reattaches.
The current window has no control that sets that cancel once Yes has started.
The identity exchange never sets `enabled`, so cleanup does not send
`MIDI_DISABLE`. The offline model uses the same order with an in-memory
script and does not sleep. The script does not know a late reply is coming:
that reply is added to the queue only after the first one is taken.

The app sends one request. After reattach, Linux's own `snd-usb-variax`
startup can send that same kind of question by itself, and it can repeat
until it sees a reply it accepts. This guitar's identity is not that reply.
That later traffic is Linux. It is not a second request from this app, and
it is not the "second answer" rule above. The second-answer rule applies
only to complete replies inside the app's own three-second window, before
the driver is given back.

## 3. Stop conditions

| Condition | Result |
| --- | --- |
| The reply is not a Line 6 identity | Stop: unknown. Cleanup runs because the connection was claimed. |
| A second complete reply arrives after the first, and still inside the same 3 second window | Stop: ambiguous. The first reply can be named. It does not pass. Cleanup runs. |
| The reply is a known Line 6 identity other than Variax 600 3.10, including the published PODxt Live 3.01 shape or a different Variax version | Stop: inconsistent. A decoded PODxt Live 3.01 identity is named in the report and does not pass. Cleanup runs. |
| No reply within 3 seconds | Stop: timed out. No further request is sent. Cleanup runs. |
| Release or reattach returns an error | Stop: cleanup failed, kept beside the original stop. A matched guitar identity is not reported as a pass. The report names both. |
| Claim fails after detach | Stop: claim failed. Release is skipped. Reattach is attempted. If reattach also fails, both errors are in the report. |
| The alternate setting fails after claim | Stop: alternate failed. Release and reattach are both attempted. A cleanup error is kept beside the prepare error. |
| The person chooses No, or closes the window before the exchange starts | Stop before any request. The driver is not detached, so cleanup is not attempted. |
| The offline model is told to cancel after detach and before the send | Stop: cancelled. Nothing is sent. Reattach is attempted. Release is attempted only if claim had succeeded. The current window cannot do this once Yes has started. |
| Stage 1 did not pass, or it passed without the expected driver binding | Stage 2 is not asked. The binding is one PODxt Live, `snd-usb-pod` on interface 0, and `snd-usb-variax` on interface 1, from this session's step 1. |

A pass is only the Variax 600 3.10 reply, with release and reattach both
succeeding. The report then says `guitar=variax-600-3.10`, `bridge=none`,
and `cleanup=ok`. A pass does not start the settings read. That step waits
for its own Yes, and its live form stays locked.

## 4. How the owner checks that Linux got the driver back

The saved steps 1–2 report says `cleanup=ok` or `cleanup=failed`. That line
is the check's own record. It is not a substitute for looking at the rig.

- `cleanup=ok` after a pass: the procedure reattached the driver, and
  released interface 1 if it had claimed it. Interface 0 was never claimed.
  This line is not the last check. Save the steps 1–2 report first. The
  button is **Save the step 2 report, then run step 1 again**. The report
  is written before Device check starts over. If the save does not succeed,
  step 1 does not restart. The new step 1 is a fresh G1 read. It must show
  one PODxt Live, `snd-usb-pod` on interface 0, and `snd-usb-variax` on
  interface 1. Then stop. POD sound should still be the sound Linux had
  before the check. If interface 1 is not `snd-usb-variax`, treat the check
  as failed: unplug the PODxt Live, plug it in again, run only step 1, and
  stop. Do not choose step 2 again unless that fresh step 1 shows the
  expected binding.
- `cleanup=failed`, or any other stop: stop. Do not send anything else.
  Unplug the PODxt Live and plug it in again so Linux can bind its drivers.
  Then run only Device check step 1 and stop. Step 1 should show one PODxt
  Live, with the POD driver on interface 0 and `snd_usb_variax` on
  interface 1. If it does not, leave the devices unused and report that
  step 1 result. The report from the failed step keeps the original error
  and the cleanup error when both happened.

The November captures do not record detach, release, or reattach. This
confirmation has not been observed on the hardware. The fake transport
covers a cleanup failure only as a scripted result.

## 5. Firmware and schematic trace

device was contacted.

  442,402 bytes, product `00070004`, version `03100000`. The universal

- The PODxt USB-component image is still a separate missing artifact
  ([#20](https://github.com/guirossibrum/VariaxWorkbench/issues/20)). The
  main-flash search does not cover it.
- [Schematic reference](../rig-schematics.md): the Variax drawing shows a
  DSP56367 and SST39LF040 flash on MG-300 MAIN sheet 2, revision A1. The

  The Live VDI-to-USB route remains open. Those limits are unchanged.
- The host driver is a different trace. `snd-usb-variax` contains
  `F0 7E 7F 06 01 F7` and accepts product `0x00070000`, so this guitar's
  `0x00070004` does not finish that startup. That reading is in
  [linux-transport.md](../linux-transport.md). It was not run, and it is
  not the device firmware.

## 6. Simulation, kept separate from the captures

`src/identity_stage.rs` feeds one scripted Variax reply after one request,
then polls again. The second poll is the rest of the three-second window.
A reply added only after the first one is taken is ambiguous. The script
is not told in advance that the late reply exists. Detach, claim, and the
alternate setting are separate steps. Release runs only after a successful
claim. Reattach runs whenever detach succeeded. A claim failure, an
alternate-setting failure, and a cancel before the send are separate
scripted results, including a cleanup failure kept beside the original
error. A passing simulation shows that the program accepted one guitar
reply and stopped. It does not replay a capture, and it does not show
what the devices would do.

The settings-read rehearsal remains stage 3. It uses the fake control
transport and still requires gate G3 before any live form. Stage 2 does not
call it.
