## 1. Proposed procedure, simulation, and historical evidence

These are three different things. A result from one of them is not evidence
for the others.

### Proposed procedure

Not authorized, and not run. If a future build is allowed to run stage 2, the
only request bytes are `read_session::IDENTITY_REQUEST`:

`F0 7E 7F 06 01 F7`

That is the universal identity inquiry already used by the read-session
allowlist (`src/read_session.rs`). The proposal sends that same request
twice: first for the PODxt Live bridge, then for the attached Variax 600
(`src/identity_stage.rs`, `run_identity_exchange`). It does not send
`midi_enable`, the two settings requests, or `MIDI_DISABLE`. Those belong to
gate G3. The consent screen says this is a proposal rehearsed in Simulation.

### Simulated behavior

The fake transport returns one bridge reply and then one guitar reply after

show what either device would do, and it does not replay a captured session.

## 2. Reply shapes used as simulation inputs

The private capture files stay local. The shapes below are the ones already
published in `src/midi.rs`
(`parses_observed_variax_ascii_and_pod_numeric_revisions`) and named in
[report.md](../report.md) for 2026-11-14. The simulation accepts these shapes
as inputs. Publishing them does not show that two identity requests were
observed. Each is 17 bytes and ends in `F7`.

| Role | Product | Version | Bytes |
| --- | --- | --- | --- |
| PODxt Live bridge | `0x0003000a` | 3.01 | `F0 7E 7F 06 02 00 01 0C 03 00 0A 00 00 03 00 01 F7` |
| Variax 600 (shared 300/600 identity) | `0x00070004` | 3.10 | `F0 7E 7F 06 02 00 01 0C 07 00 04 00 30 33 31 30 F7` |

The guitar revision is ASCII `0310`. The bridge revision is the numeric bytes
`00 03 00 01`. Any other product, or either of these products with another
version, does not pass.

## 3. Interface 1, then put it back

The live procedure, when a future build is allowed to run it, uses the
existing session in `src/usb.rs` and touches interface 1 only. Interface 0
stays with `snd-usb-pod`. The steps below are what that code does today. This
round does not call it. `Session::open` is reached only from `read_current`,
which returns at the G2 lock before any USB enumeration (`usb.rs` test
`hard_lock_blocks_before_usb_enumeration_or_open`).

| Step | Where | Bound |
| --- | --- | --- |
| Find the one `0e41:4650` device | `Session::open_unlocked` | Stop if the count is not 1 |
| If a kernel driver is active on interface 1, detach it | `kernel_driver_active(1)`, `detach_kernel_driver(1)` | Interface 1 only |
| Claim interface 1 and select altsetting 1 | `claim_interface(1)`, `set_alternate_setting(1, 1)` | Interface 0 is not claimed |
| Send the 6-byte request on interrupt OUT `0x05` | `write_interrupt`, 16-byte chunks, 1 second timeout, 5 ms between chunks | One request per device |
| Read interrupt IN `0x86` | 100 ms polls, 3 second reply budget (`read_session::receive`) | Cancel checked on each poll |
| Release interface 1 | `cleanup` when `claimed` | Record the error and continue to reattach |
| Reattach the kernel driver on interface 1 | `attach_kernel_driver(1)` when `detached` | A failure stops the sequence |
| Drop | `Drop` calls `cleanup` again | A second cleanup is harmless once the flags are clear |

Identity-only work never sets `enabled`, so cleanup does not send
`MIDI_DISABLE`. Cancel before the first request sends nothing, and cleanup
still runs. Cancel after the bridge reply sends no guitar request, and
cleanup still runs. The offline model uses the same order with an in-memory
script and does not sleep.

## 4. Stop conditions

| Condition | Result |
| --- | --- |
| The reply is not a Line 6 identity, or the product is neither device above | Stop: unknown. Cleanup still runs. |
| One request has more than one reply, or the second reply repeats the bridge | Stop: ambiguous. Cleanup still runs. |
| The guitar answers where the bridge should, or a version is not 3.01 / 3.10 | Stop: inconsistent. Cleanup still runs. |
| No reply within 3 seconds | Stop: timed out. The second request is not sent. Cleanup still runs. |
| Release or reattach returns an error | Stop: cleanup failed. A matched pair is not reported as a pass. If identification already failed, that failure is kept as well. |
| The person chooses No or closes the window | Stop before any request, as in stage 1. |
| Stage 1 did not pass | Stage 2 is not asked. |

A pass is only the bridge 3.01 followed by the guitar 3.10, with release and
reattach both succeeding. A pass does not start the settings read. That step
waits for its own Yes, and its live form stays locked.

## 6. Procedure for the owner to review

This is the one-page procedure. Authorization stays pending until the owner
gives direct permission for it in a working session. Reviewing this page is
not that permission.

1. Stage 1 has already passed, and you give a separate Yes for stage 2. The
   answer starts as No.
2. The app would detach the kernel driver from PODxt Live interface 1 only,
   claim that interface, and leave interface 0 alone.
3. The proposal would send `F0 7E 7F 06 01 F7` once for the PODxt Live and
   once for the Variax 600. The simulation is willing to accept 3.01 then
   3.10. The 2026-11-14 capture does not show that two-request exchange.
4. It would attempt to release interface 1 and reattach its driver after
   success, timeout, cancellation, or an invalid reply. A cleanup failure
   stops the check and is recorded alongside any earlier failure.
5. A bad or missing identity stops the sequence. Nothing is written to either
   device. The saved report uses fixed words only.
