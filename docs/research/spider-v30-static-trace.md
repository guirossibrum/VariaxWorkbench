**V30 static** identifies a model-specific artifact or explicit branch. **Family static** identifies a shared Parker/Spider path. **Candidate** identifies a cross-build inference or shared-engine clue. **Open** identifies a missing link. All hardware behavior remains unverified.

In both identity routines one virtual send carries `f0 7e 7f 06 01 f7`. The following two receive windows are visible in both builds.

1. Up to two reads with 200 ms spacing. The checked packet length is 17 and the tests cover `7e` at byte 1 and `06 02 00 01 0c` at bytes 3–7.
2. Up to ten reads with 100 ms spacing. The code tests length ≥12, manufacturer `00 01 0c` at bytes 1–3, the object's device field masked to seven bits at byte 4, and `06 02` at bytes 8–9. Subtype at byte 5 maps 0 to V30 and 1 to V60, with 2–5 assigned to the other family members. There is no second explicit send within either routine. A bounded read model should separately validate the envelope, actual string extents and supported subtype before accepting the reply. The observed minimum-length predicate alone covers a header.
3. Both builds probe a mode string at byte 22. Main mode sets state 1, updater mode state 3. Main-mode code also derives a version from a string. The original interpretation of every trailing field and observed wire lengths remain open. Exhausted receive windows return `0xffffdb46` in both builds.

Windows Updater 1.28 corroborates the two-read query and port structure. Diagnostic xrefs `0x004997c9` → `0x007f8b24` and `0x00497825` → `0x007f8258` locate its query and normal-mode setup. Its `0x0049b650` has distinct Interposer, MIDI and USB platform object branches. The Remote generic libusb open/claim and reset imports are separate evidence from ordinary editor message flow.

## Parker SysEx transport and lifecycle

Windows Remote RTTI `0x10191014` → complete-object locator `0x10178460` → virtual function table at `0x101737f0` identifies `L6ParkerMidiMsgPortMultiplexor`. Its send is `0x10057810` (table pointer `0x101737fc`), receive is `0x10057aa0` (pointer `0x10173808`). The macOS Remote RTTI pointer at `0x10036d880` leads to send `0x1000be25a` through `0x10036d8b0` and receive `0x1000be64c` through `0x10036d8c8`. Windows Updater send `0x004a0700`, header builder `0x004a05e0`, packer `0x004c2170` and receiver `0x004a0260` independently corroborate the shared framing. The symbolized macOS Updater has `write` at `0x1001033b0` and `handleReceive` at `0x100103fc0`.

- The send envelope is `f0 00 01 0c 22 <subtype> 4d <port> <sequence> <fragment> <length-high> <length-low> … f7` in Windows Remote. Both length fields are nibbles of raw fragment length minus one. Sequence is a seven-bit counter per logical port. Fragment starts at zero. The sender chunks at 210 raw bytes and waits 5 ms between fragments when sending more than one.
- The body packs each group of seven raw bytes into a mask and seven seven-bit values. Mask bit 6 corresponds to the first byte, bit 0 to the seventh. A short final group is zero-padded. The length fields retain the unpadded count. The receive branch checks manufacturer and message class, matches device subtype, looks up the logical client and restores high bits. It forwards the declared raw length to that client. This is an envelope-level dispatch map. The librarian handler below adds inner request and completion evidence. Editor messages and device-side fragment completion still need tracing.
- Windows Remote `0x100569f0` dispatches connection and handshake failures into different state transitions from success. The editor code should distinguish a failed port or identity, a late reply after disconnect, a benign current-preset notification and a storage outcome. Candidate notification names include `EditBuffer_ParamChanged`, `EditBuffer_PresetChanged`, `EditBuffer_DevicePresetChanged` and `EditBuffer_PresetSavedToDevice` at macOS file offsets `0x31ab15`–`0x31abc3`. These are event interfaces and do not establish underlying command or acknowledgement bytes.

## One later read and the editing boundary

- **Family static.** macOS Remote `0x1000fcdb8` is a second, firmware-guarded query path. It constructs class `0x7c` under the Parker manufacturer/family/subtype header and uses the same base-port send/receive virtual slots as identity. The response checks the header and subtype, collects a packed body before the SysEx terminator, and invokes the same unpacker as multiplexed traffic. Xref `0x1000fcee0` → `0x100077ec4` anchors the unpacker. The result has length, component/version and mode-like fields. Their complete semantics are open. Keep this additional query out of the first identity card.
- **Family static at the engine boundary.** In Windows Remote, xref `0x10026fd5` → `0x10172420` joins the current-tone store key to dispatcher `0x10026af0`. It builds the logical preset-slot target, calls a virtual method at byte offset `+0x134`, dispatches an error on a negative result, then on success waits 500 ms and follows refresh and reload paths. The reload uses virtual offset `+0x138`. The original delay and reload alone do not establish device acknowledgement or a verified read-back.
- **Cross-checked application targets.** Windows archive xref `0x1002650c` → `0x10172344` leads to `0x10025300`. This dispatcher uses a preset-group target for archives and a separate binary-preset slot target for binary export. macOS dispatcher `0x10007db90` builds the same logical targets. The Windows dispatcher wraps preset navigation across indices 0–127 and selects the slot through `+0x138`. This is a client range candidate for V30. A bounded read-only listing needs independent proof of the V30 reported slot count and confirmation that reads do not activate slots.

## Librarian transactions after the SysEx envelope

Windows Remote assigns the Spider product range to the Parker seed and constructs the editor and V2 librarian interfaces in `0x10078e90`. The `A36EditorLibrarian` table at `0x10175270` resolves the store/reload virtual offsets to `0x1007d080` and `0x1007d610`. For a device target the store calls `0x1006c3c0`, which serializes current state and invokes the librarian writer `0x1009c740`. The navigation route calls `0x1006c040`. Its Spider branch selects the requested slot first via `0x1009c8d0` and then reads the current buffer with index `0xffffffff` via `0x1009c6a0`. A standalone buffered read enters `0x10085d50`, which distinguishes the current-buffer sentinel from a numbered slot and can return an already-cached numbered preset.

These operations resolve through `ToneMatchLibrarian_Remote` at Windows table `0x10176334`. The corresponding macOS type name is at `0x100307f20`, typeinfo at `0x10036c0a8` and the typeinfo slot immediately preceding the callable entries at `0x10036c018`.

| Operation | Windows Remote | macOS Remote | Observed contract |
| --- | --- | --- | --- |
| Read preset/current buffer | `0x1009d4b0` | `0x1000555ba` | Inner command `0x0b` with one 32-bit index. Windows waits 15 s. macOS waits 1 s in this wrapper. Completion returns the received length excluding a four-byte status. Open on actual V30 examples, device-side slot-read side effects and complete preset-body format. |
| Store serialized preset | `0x1009d570` | `0x100055664` | Inner command `0x0c` or `0x0f` selected by a flag, with index and serialized length followed by data. Both wait 15 s for completion. macOS adds 300 ms after a completed wait. The normal device-slot route passes the zero form through the Windows wrapper. Wire success is distinct from persistence. |
| Select slot | `0x1009d630` | `0x10005570e` | Inner command `0x0d` with one 32-bit index. Both wait 15 s. For the Windows Spider navigation path this precedes a buffer read and changes the setup under inspection. |
| Write request header | `0x1009cd00` | `0x100054ccc` call sites | Native 32-bit command and declared payload length followed by operation fields. The Windows routine allocates a pending transaction token and may split header and data at the port API. This token is host bookkeeping. |

Windows receiver `0x100861d0` reads an eight-byte inner header from the librarian port. It calls `0x1009d820` on response class 1 (xref `0x10086271`). The handler removes the next pending token, bounds the declared reply length, reads the four-byte status where expected, then collects body bytes. This path uses queue order and response class. It has no observed echo of the request opcode or slot. Timeout cleanup at `0x1009dad0` completes and clears pending tokens. This evidence supports one in-flight Workbench librarian transaction per attachment and rejecting late results by generation. The post-store reload still calls slot selection. No capture establishes what the status means during an interrupted flash write or whether the reload verifies exactly what was stored.

## Volatile transfer and binary preset leads

Windows Remote has a separate current-buffer send path. In `0x1006f540`, the guarded send branch takes the serialized buffer and calls `0x1009c740` with index `0xffffffff`. A mode flag accompanies this send. The librarian accepts that sentinel even though it rejects out-of-range numbered slots, and its wrapper skips numbered-slot cache invalidation for the sentinel. This distinguishes an edit-buffer upload from a numbered store at the host call boundary. It leaves individual parameter sends, complete payload structure and observed hardware side effects as separate gaps.

Windows serializer `0x1008e850` initializes a version-2 record writer with the word `0x50525350` (little-endian bytes `PSRP`). The related parser at `0x1008b570` tests that same word. The serializer has named-key branches such as `NamePSKey` and `LabelPSKey`. This gives an anchor for dissecting numbered/current preset bodies. It does not establish byte coverage of every field or the outer disk preset/archive wrappers.

## Preset and catalogue evidence

- **Family static.** macOS package Readme associates `.svl6p` with presets and `.svl6a` with archives. In the executable `0x10010865a` passes `.svl6p` to its file-type setup. `0x100027f34` recognizes schema `L6Preset`. `0x1000277f4` and `0x1000284e0` feed that schema to the shared writers. `0x1000c2bf2` calls the version 1 `L6PresetBundle` writer with optional zlib. The package association and generic bundle writer are independent anchors. A complete archive-to-writer join, compression wrapper and slot preservation guarantee still need a saved sample or closer call trace.
- **Cross-checked family data.** Both builds ship identical parsed `default_preset_parker.json`. macOS `0x1000422f8` maps the `0x220000..0x220005` range to the Parker preset, and the Windows default-symbol resource is referenced at `0x101755dc`. The seed is schema `L6Preset`, version 5. It has `data.device`, `data.device_version`, `data.meta` and `data.tone`. The seed actually identifies product `0x220002` (V120). It establishes shared edit shape and example keys, with V30-specific availability still open. Its tone has amp, cab, three FX blocks, reverb, compressor, gate, EQ, volume, wah and global fields. The file can represent post placement, bypass, mix, tempo sync, speaker mode and tweak/pedal assignment.
- **Cross-checked family catalogue.** The eight shared JSON files carry 206 model or fixed records and 1,343 parameter rows. Counts by catalogue are 79 amp, 26 cab, 15 delay, 9 fixed, 23 modulation, 15 reverb, 31 stomp and 8 wah. Each entry can carry numeric and symbolic model IDs, category, display data, defaults, range and type. Values show normalized scalar 0–1, integer choices, booleans and strings. Examples include tempo 30–240 with default 120, cab mic selectors 0–3 where present, and tempo-note selectors 1–14. On-disk display bounds and scales are separate from wire encodings and actual V30 availability. At least one delay entry has a device allowlist that excludes Spider IDs. Shared HD, IR and other-family branches require explicit model checks before offering a control.
- **Cross-checked family symbols.** Both `defaultSymbolTable_Parker.bin` files are byte-identical. The little-endian header holds count 910 and total length 22,074. Records are 12 bytes with name-pool offset, string CRC-32 and byte length excluding NUL. The pool begins at `0x2ab0`. All 910 names are non-duplicate and all their CRC-32 values recompute. Symbol CRC, model ID and a wire parameter key are distinct representations until a caller connects them.
- **Family UI leads.** The macOS librarian call sites `0x1001e26a0`, `0x1001e1cd0`, and `0x1001cb500` reference import, export and binary export messages. Windows has corresponding managed metadata and native exports for renaming and reordering. macOS dialogs distinguish unsaved current edits from stored contents and warn before overwriting or reloading. The librarian command layer is mapped above. Full preset-body decoding, persistent acknowledgement, read-back, atomicity and active-buffer preservation during bank acquisition are open.

## Driver, maintenance and firmware

**Windows driver.** The INF associates V30 with the AMD64 service and registers audio and MIDI capture/render categories. The main SYS entry at `0x140035520` has KMDF binding imports. The filter entry at `0x14001e000` calls `0x1400012a8`, whose diagnostic and call lead to `KsInitializeDriver`. The driver package has both x86 and x64 user-mode Interposer backends. Ghidra shows Interposer initialization at `0x100013f0`, pipe dispatch at `0x10001730` and messages at `0x10001a10`. The wrappers delegate to backend virtual calls. The package's x86 backend imports `DeviceIoControl`. WinMM and Interposer can therefore be evaluated as distinct Windows adapter candidates. Driver ownership, actual normal-mode route and coexistence with audio remain open. The INF also has a Catalyst-named registration string amid Spider services. Its runtime effect is unresolved. Audio pin names and ASIO availability are static package facts.

**Vendor maintenance.** Mac Remote has a V30-specific firmware UI definition, and Windows has updater-related resources and shared engine branches. Central's `SpiderVSteps.json` is parsed-identical across platforms and has six model IDs, a maintenance state machine, licence display, DFU/reprogramming states and failure/success paths. Windows Central selects this resource at `0x1025bab0` (xref `0x1025be33` → `0x10485b4c`). The x86_64 macOS selection is `0x10010630e` (xref `0x100106388` → `0x10057a64b`), and arm64 is `0x1000f7db0` (xref `0x1000f7ed8` → `0x100508533`). The resource has additional G10T maintenance states. The symbolized macOS Updater predicate `doesDeviceSupportEmbeddedWirelessReceiver` at `0x1000f1e60` accepts product IDs `0x220001..0x220004`. Its V30 branch is outside that range. Treat built-in wireless as unsupported in the V30 profile based on this artefact. Updater's startup and mode handling demonstrate that editor and boot/update behavior diverge. Its converter at `0x00497880` (xref `0x00497ab1` to diagnostic `0x007f8f88`) is guarded by a device field. It bridges via temporary files to a native converter at `0x0049cfa0`. Applicability of that branch to the pinned SVU remains open.

**Firmware correlation.** The Workbench offline inspector independently parses the SVU as product `0x00220000`, version word `0x02050030`, with one type-0 region spanning the 393,192-byte inflated image. It currently classifies the product as unknown. Remote, Central and the INF independently identify the same V30 logical product or USB binding. The V60 desktop mapping is the adjacent product ID. The pinned filename claims V30/V60 applicability, while the container declares only the V30-numbered product word. Eligibility of V60/MkII or any board revisions needs an updater compatibility join or additional pinned evidence. No internal firmware decode, runnable instruction architecture, flash partition labels or runtime parity is established.

## Offline verification

`verify_offline_v2.py` in private evidence passed 14 checks covering eight pinned source hashes, SVU structure and digest, the shared resource pairs, all 910 symbol records, both identity request constants and synthetic malformed/timeout/subtype paths. The suite also checks a fixed encoded frame, all 210 supported fragment lengths, a three-fragment split and malformed frame rejection. Synthetic identity fixtures are header-level examples. They contain no device capture. The independent Workbench inspector result is in `workbench-svu.log`. Raw code, strings, executable bytes and vendor data remain in private backups.
