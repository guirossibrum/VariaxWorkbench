# Spider V30 offline audit · feature gaps and Workbench integration

[Issue #311](https://github.com/guirossibrum/VariaxWorkbench/issues/311) · [Inventory](spider-v30-inventory.md) · [Compiled-code and format evidence](spider-v30-static-trace.md).

The first deliverable that can run without a V30 is a read-only local preset viewer. The first device slice needs an independently implemented V30-only MIDI identity path, explicit attachment selection, and a Rig Check card. The Windows driver and the editor engine are separate components. Device discovery, control and audio may use different OS interfaces.

Evidence scope in the matrix is **V30 static**, **family static**, **candidate**, and **open**, as defined in the [static trace](spider-v30-static-trace.md). No row claims hardware verification. Where a shared catalog or engine has controls for other devices, the Spider profile should hide them until the model and firmware are established.

## Independently reviewable implementation slices

1. **Local viewer and parser.** Add Rust types for Spider product, document versions, field identifiers, typed values, layout and evidence-scoped capabilities. Keep the file representation separate from edit/session state. Connect the new family to registry and document tabs. Begin with read-only inspection of synthetic and private owner-supplied files. A separately sourced, minimal, provenance-tracked catalogue is a potential package input after review. The pinned artifacts serve as private analysis oracles. Use normal UI file selection and verify native package launch offline on Linux, macOS arm64/x86_64 and supported Windows builds.
2. **Passive detection and first identity.** Add a Spider family protocol module, fake byte transport, response validation, attachment binding and closed-by-default Rig Check approval for this new rig. Stabilize the V30 receive limits and mode parsing first. Linux should evaluate ALSA sequencer/raw MIDI mapping and read-only descriptor match. macOS should evaluate CoreMIDI source/destination pairing and existing device inventory with native arm64 and x86_64 builds. Windows should evaluate WinMM and supported Windows MIDI APIs on the supported OS and map endpoints to SetupAPI attachment data. Treat Interposer and direct USB as independent candidates, requiring evidence before any claim, vendor dependency or device rebind. A platform with unproved access can ship the local viewer.
3. **Read-only editor and library.** Trace client-level commands, format and reply IDs for metadata, current buffer, selected stored tone and full listing. Prove the stored-read path leaves the active slot and dirty buffer intact, or expose the actual switching behavior under its own approval. Add bounded snapshots, export and backup with explicit partial/completeness status. Cover all emitted request classes in Rig Check and use fake late replies and disconnects in CI.
4. **Live edits, then stores.** Release volatile edit first and store/rename/reorder/restore only as independently reviewed changes. Confirm original values and companion fields, retain backup evidence and require checked read-back. Use the project's hardware-gate procedure for approvals, one fresh session per owner run, clean release and read-only remainder after failure. Define, observe and test both rejection and ambiguous outcome. Each operation needs its own static trace or project-approved evidence and Rig Check coverage.
5. **Audio.** Review descriptors, endpoint ownership, input/output streams, rates, channel maps and contention independently of editing. Choose the thinnest native adapter per platform. Use prepared fake handles before the separate owner audio authorization. Keep vendor ASIO and Apple driver dependencies outside the requirement for a normal local editor.
6. **Maintenance.** Limit the first maintenance slice to inspecting a user-provided archive and displaying known/unknown target metadata. Keep update, reboot, DFU, recovery and resets outside product scope. Keep local tab behavior independent of Central, Updater and online services.

### First bounded owner card

Prepare this only after the V30 transport and matching rules pass review and the owner authorizes the procedure. The first card selects exactly one verified V30 candidate on one host and performs only the observed inquiry. Record the OS/build, selected physical attachment, endpoint provenance, VID/PID, received identity subtype and response timing, and the firmware string if length, type and mode are validated. Confirm PID `0e41:5068` and logical product `0x220000` together, then close and record release. Abort on absent or ambiguous endpoints, unsupported mode, writer contention, timeout, mismatched product, or disconnect. The original two-read pattern can be tested in Practice with synthetic replies and a late reply after closure. This first card has no slot changes, configuration changes, resets, account calls, writes or audio.

## Evidence still needed

The artifacts establish the first exchange, shared outer framing, document/catalogue shape and several library action boundaries. The librarian trace establishes read, select and store commands, and a Windows reply queue. The next bounded audits are to validate the current and numbered preset bodies against private samples, follow a volatile parameter change through the editor port, and establish durable store read-back. Open evidence includes editor field-to-wire bindings and units, full reply/fragment semantics, platform-to-physical endpoint binding, an authentic V30 preset/archive sample and eligibility beyond the V30 product branch. The pinned firmware body has no recognized inner map yet. Keep these gaps on #311 for Gatekeeper review.
