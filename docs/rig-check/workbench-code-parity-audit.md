# Rig Check and Workbench device code parity

[#309](https://github.com/guirossibrum/VariaxWorkbench/issues/309) compares
`rig-check` with `variax-workbench-gui`, including its **This computer**
Device Check, at `9d1bd20e7b15b6e885e4dc61b471752e65f5ec7b`. The connected
profiles cover Linux and the two macOS slices. The Mac and Windows offline
packages establish where the same source tree deliberately selects stubs.
The rig is PODxt Live 3.01 with a Variax 300/600-family reply at 3.10. The
identity reply alone cannot distinguish a 300 from a 600.

The main gaps are Workbench's Mac Variax admission and editor transport
coverage, the difference between the PODxt staged Send and live CC paths,
and the bounded PODxt reads that some older callers bypass. A passing Rig
Check step verifies the hardware exchange and starting conditions of that
step. Editor admission, scheduling, retries, cleanup and UI state need
evidence at the Workbench entry point.

## Entry points, gates and session factories

| Label | Entry and session lifetime |
| --- | --- |
| **R-P / R-V** | [Rig Check binary](../../src/rig_check/bin.rs#L184) → [step dispatcher](../../src/rig_check/steps.rs#L157) → [with_podxt / with_variax](../../src/rig_check/procedures.rs#L117) → [RealPort](../../src/rig_check/port.rs#L305). Each step constructs a `Session` with a step-specific operation allowlist and report logging. Linux caches `RawMidiLink::open(PODXT_LIVE_CARD, Path::PodxtMidi)` for PODxt and opens `UsbInterfaceLink::open(VARIAX_VIA_PODXT_LIVE)` with the rig lock as needed. Mac uses IOKit inventory plus libusb attachment matching, rechecks the registry generation before claims and holds the matched lock in `RigScope`. `DirectUsb` finishes the active interface before switching between PODxt MIDI interface 0 and Variax interface 1. The Variax session requires expected SysEx. |
| **W-P** | [PODxt LivePanel](../../src/families/podxt/editor/live_panel.rs#L173) → `with_session` / `with_platform_link`. An editor operation checks the verified attachment, unresolved-current-reply flag and rig lock before opening. Linux resolves the detected USB path and unique ALSA card to `RawMidiLink::open_device`. Mac uses [with_workbench_link](../../src/podxt_live.rs#L1192) with the tab's USB path/address and explicitly finishes the interface-0 link. Read, edit and store have separate policies. Follow holds a worker session until stopped. |
| **W-V** | [Variax attachment-scoped editor](../../src/families/variax/editor/procedure_device.rs#L298) uses Linux-only `open_variax_bridge_borrowed` on the verified USB path/address, a rig lock, shared family identity and per-mode request policy, then explicit cleanup. [Refresh](../../src/families/variax/editor/refresh.rs#L299) has its own worker and policy. [Follow](../../src/families/variax/editor/follow.rs#L464) uses a yieldable `FollowDeviceLock` and the same borrowed interface-1 opener. Mac can admit a Variax tab through its separate identity worker. The editor's native Get, Follow, download/refresh, live send and device Sync adapters are Linux-only at this revision. |
| **DC** | [Workbench Device Check window](../../src/gui.rs#L739) → `ProbeSession<RigBackend>` with default No on staged prompts → [HostRig](../../src/device_probe.rs#L1170) for G1–G3. On Mac, G1 supplies the attachment, G2 borrows its interface 1 and G3 scopes interface 1 then interface 0. Linux uses the separate bounded identity USB adapter, then the family interface-1 and ALSA readers for G3. Backup and PODxt Try/Select are separate confirmed workers in the same window. They use [library_backup](../../src/library_backup.rs#L28) or [podxt_live](../../src/podxt_live.rs#L692). Mac PODxt uses `with_workbench_link(None)` and requires a unique libusb attachment. Linux PODxt uses `RawMidiLink::open_spec`. Linux Variax full backup borrows the verified attachment. The older settings backup has its own open/reopen wrapper. |

The [hardware gate constants](../../src/hardware_gates.rs) and the
[step catalogue](../../src/rig_check/catalogue.rs#L170) are the source for
G1/G2/G3/G5/G6/G7 below. DC has separate G3 read, G5 backup, G6 Try
and channel-selection switches. W-P adds `KeepLiveEdit` for edits and
uses `DeviceCheckChannel` for selection. App-specific first-run switches
apply independently of the open hardware gates. Rig Check checks its
[step approvals](../../src/rig_check/approvals.rs) and requires a Run
choice. The [runner](../../src/rig_check/runner.rs) restricts writes after a
failure, requires applicable earlier passes and typed store confirmations,
and stops traffic on unknown store state apart from USB cleanup. Practice
uses `PracticePort`, so Practice results cover simulated behavior.

### Three Mac identity routes

1. **Rig Check 3.1.** `RealPort::open_direct_usb` checks the matched
   registry entry and opens interface 1. A strict family session calls
   `identify_if_present_retrying_silence`. An orphan tail can trigger a
   resend immediately. Complete silence can trigger one after 2 seconds.
   Other invalid data follows the failure path. The step can ask the owner
   to check VDI and explicitly continue after a silent exchange.
   [Port](../../src/rig_check/port.rs#L349) · [Step](../../src/rig_check/steps.rs#L627) · [Family exchange](../../crates/line6-devices/src/family/variax.rs#L186)
2. **Workbench automatic / Refresh guitar.** The Mac discovery job
   verifies its own attachment candidate and uses the same interface-1
   opener. Its strict family session calls `identify_if_present`, which
   may resend for an orphan tail and returns no identity after complete
   silence. It explicitly finishes the link before publishing the guitar
   status. Initial discovery previously verified PODxt on interface 0.
   [Mac worker](../../src/app/detection/identity.rs#L205) · [Family exchange](../../crates/line6-devices/src/family/variax.rs#L196)
3. **Workbench Device Check G2.** The staged host backend takes its candidate
   from G1 and opens interface 1 through the same borrowed USB opener.
   `MacIdentity` supplies its own `SysexDecoder`, receive window and
   cleanup adapter to `run_identity_exchange`. The bounded exchange sends
   one request, checks the result and finishes even when it times out.
   Linux DC also uses that exchange with a separate native USB adapter.
   Linux automatic discovery selects `run_discovery_exchange`, which
   permits a single resend only for an observed orphan tail.
   [Mac G2 adapter](../../src/usb.rs#L439) · [Policy entry points](../../src/identity_stage.rs#L674) · [Linux discovery](../../src/usb.rs#L619)

The earlier report demonstrates a silence case where the Rig Check retry
mattered on this rig. The completed continuation records two requests but
its count alone cannot distinguish silence from an orphan tail. The
Workbench failure is consistent with the source-policy difference.
Attachment, timing and received bytes at the Workbench failure remain
unobserved. The G2 one-request authorization is an explicit product
constraint.

### PODxt Live editing and staged Send

The editor initially stages changes. Its pending list coalesces the latest
value per control and the preview overlays pending and in-flight values.
Changing a control in this mode does not send. **Send to POD** takes those
targets through `EditorEdit::Send`, checks the expected playing channel,
current tone and packs, builds the updated full edit-buffer payload and
verifies the transfer. **Clear staged edits** clears the local queue.

With **Live editing** enabled and a verified current snapshot, the poller
dispatches `EditorEdit::Controls` automatically at a minimum 150 ms
interval between dispatches. This sends the verified changed CCs (two for
some compound settings), checks the readback, and leaves the edit playing
without a store. On a failed edit the UI clears pending work and requires
a fresh Get. **Undo live edits** uses the preserved snapshot and checks the
restored tone. Both edit paths depend on G6 and `KeepLiveEdit`.
`WHOLE_TONE_SEND_APPROVED` controls the separate Resend action.
The staged-mode screenshot verifies only the visible mode. Rig Check 4.1
exercises the family Drive/Tempo CC and Undo path, and 4.6 verifies the
own-byte whole-tone transfer. Neither runs Workbench's queue, staged
payload construction, snapshot lifecycle or macOS worker.

## Source-file and build-profile reuse

The root [manifest](../../Cargo.toml) builds the two binaries against
`variax_workbench` and the local [line6-devices crate](../../crates/line6-devices/Cargo.toml).
A library module can be compiled into the library for a profile while only
one executable calls it. The table distinguishes compiled source selection
from call reachability. It is a source/manifest inspection, with no claim
about which unused sections a native linker retained.

| Build path | Target and selected code |
| --- | --- |
| Paired owner Linux | [build-owner-pair.sh](../../packaging/build-owner-pair.sh#L94) builds both bins in `--release --locked --offline --no-default-features --features gui,portable-math,usb`, with the same source revision. Linux selects raw MIDI for PODxt and libusb for Variax. Unix locking and Linux MIDI use `libc`, directly in the device crate. The Linux host libusb build can use the system library via pkg-config or fall back to vendored C. |
| Ordinary Linux builds | Cargo defaults to `gui,usb`. The [standalone Rig Check package](../../packaging/rig-check/build-linux.sh#L31) uses these defaults. [Workbench Linux package builder](../../scripts/package_linux.py#L67) retains defaults and can add `portable-math`. Host math is selected when `portable-math` is absent, so ordinary defaults and the paired owner release differ even at one revision. |
| Mac owner USB | [build.sh](../../packaging/macos/build.sh#L59) builds both bins for `x86_64-apple-darwin` (10.15) and `aarch64-apple-darwin` (11.0), with `--release --no-default-features --features gui,portable-math,usb`. The Mac target forces vendored `rusb` 0.9.4 → `libusb1-sys` 0.7.0 → Darwin C backend with system frameworks. `line6-devices/usb` also activates the Mac-only [macos-usb-inventory crate](../../crates/macos-usb-inventory/Cargo.toml), which uses IOKit and CoreFoundation for passive enumeration. On Linux the Rig Check PODxt `RealPort` branch still compiles against ALSA without `usb`, with no Variax link. |
| Shared feature/dependency effects | `gui` selects eframe/winit Glow GUI dependencies, PNG image decoding, the non-Mac file-picker dependency and `podxt-table`. `portable-math` selects libm 0.2.16 with forced software float operations. `usb` selects root `rusb` and `line6-devices/usb`. [.cargo/config.toml](../../.cargo/config.toml) sets dev/debugging symbols separately from the release profile. |

### Source inputs and package contents

- The vendored Rust/C USB tree supplies build inputs. Mac statically uses
  the vendored libusb backend and verifies system dylib dependencies, both
  minimum OS versions and USB symbols by profile. Universal assembly uses
  `lipo` and the bundle has an ad-hoc signature.
  [Mac build](../../packaging/macos/build.sh#L98) · [Package verifier](../../packaging/macos/package.py#L148)
- The re-packaged model data `assets/variax-models/legacy.vxm.zlib` is a
  shared embedded renderer input. Rig Check also embeds derived/synthetic
  engine evidence in `engine_check.rs`. The GUI's `podxt-table` selects
  the embedded PODxt parameter JSON. These are data inputs with different
  consumers. Original reference material remains private.
  [Model provenance](../../assets/variax-models/SOURCES.md) · [Engine evidence](../../src/rig_check/engine_check.rs#L29) · [PODxt table](../../src/families/podxt/file/parameters.rs#L7)
- The Mac DMG includes two separate apps and opening instructions. Each app
  has its own executable, Info.plist and icon. Workbench also gets ten approved
  runtime artwork files and their manifest under Resources. The Windows
  offline ZIP contains the two executables, instructions, build info and
  checksums. The paired Linux bundle carries both executables, Rig Check
  docs and verification metadata. The standalone Rig Check distribution
  adds a launcher, and the Workbench install layout includes desktop/MIME
  files, icon, docs and third-party notices. Those payloads are package
  contents. Their presence cannot establish source or procedure parity.
