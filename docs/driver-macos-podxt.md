# PODxt Live macOS driver

Evidence labels distinguish **Static fact**, **Inference** and **Unknown**. Addresses refer to the named Mach-O slice. Scope is the locally extracted Line 6 Audio-Midi Driver 7.6.8 package.

## Inventory

| Binary | Static fact — architecture, version and external interface | Inference — loader |
| --- | --- | --- |
| `Line6MIDI.plugin/Contents/MacOS/Line6MIDI` | Universal x86_64 and i386 bundle, both plist versions 7.6.8. Factory and only global defined text symbol `_NewL6MIDIDevManager` at `0x1a70` (x86_64) and `0x1b90` (i386) | CoreMIDI server via CFPlugIn registration |
| `Line6AudioSigned.kext/Contents/MacOS/Line6Audio` | x86_64 only, both plist versions 7.6.8. Kernel symbols include `com_line6_audio` class, `com_line6_driver_isoenginext` and local `__start` at `0x9c75f` | IOKit kernel extension matching registered USB personalities |
| `L6TWX_u.dylib` | i386 only. Embedded install ID under `L6TWXY.framework/Versions/A/data/twx/`, compatibility/current version 1.0.0. Exports the `TWX*` interface listed below | A Line 6 application or framework client, exact consumer in this distribution unknown |

**Static fact.** The MIDI plug-in links Carbon, IOKit, CoreMIDI, CoreFoundation, libstdc++ and libSystem. Its i386 slice also links CoreMIDIServer. Undefined symbols include `IOServiceMatching`, `IOConnectCallMethod`, `IOConnectCallAsyncMethod` and `MIDIDeviceCreate`. Its plist gives the CFPlugIn factory and type UUIDs, without a USB VID/PID personality.

**Static fact.** The kext's `OSBundleLibraries` declares AppleUSBMergeNub, IOAudioFamily, IOUSBFamily, and the iokit, libkern and mach KPIs. Kernel undefined symbols include `IOUSBDevice` and `IOUSBInterface` methods. It exposes kernel C++ class symbols and associated vtables. Under vendor `0x0e41`, PODxt `0x5044`, PODxt Pro `0x5050` and PODxt Live `0x4650` each have a `com_line6_audio` personality for `IOUSBInterface`, configuration 1, interface 0. Each also has two `IOUSBDevice` personalities, `AppleUSBMergeNub` and `AppleUSBComposite`. The interface-0 personality agrees with the POD side of the [Linux split](linux-transport.md). The device-level personalities alone give no evidence about interface-1 transfers.

**Static fact.** `L6TWX_u.dylib` links SystemConfiguration, Carbon, CoreAudio, CoreFoundation, CoreMIDI, CoreServices, IOKit, ApplicationServices, libcrypto, libstdc++, libgcc and libSystem. The 15 global text names are `TWXBeginDecrypt`, `TWXCommandInterface`, `TWXDecrypt`, `TWXEndDecrypt`, `TWXExit`, `TWXGetHardwareDeviceInfo`, `TWXGetLastErrorA`, `TWXGetLastErrorW`, `TWXGetNumHardwareDevices`, `TWXGetVersionA`, `TWXGetVersionW`, `TWXInit`, `TWXIsValidAsset`, `TWXLaunchMonkey` and `TWXVersionToString`. It has no separate USB matching plist in the examined payload and is absent from the MIDI plug-in's dependency load commands. The [prior USB firmware analysis](pod-usb-firmware.md) records Line 6 device-manager classes inside the dylib.

**Inference.** These Intel binaries provide no native Apple Silicon driver. An Intel slice in the user-space MIDI bundle does not supply an ARM64 kernel driver. **Unknown.** The host versions that will accept the legacy Intel package and the exact process that loads the TWX component.

**Static fact.** Inventory can be reproduced with `file`, Python `plistlib` and `llvm-objdump --macho --arch=<slice> --dylibs-used --syms`.

## CoreMIDI plug-in and kernel MIDI transport

| Stage | Static fact — x86_64 disassembly |
| --- | --- |
| Driver discovery | `Line6MIDI` registers an IOKit first-match notification for `com_line6_driver_midi` at `0x21d4`–`0x2201`. For PID `0x4650` its setup matches the PODxt Live icon at `0x1dc4`–`0x1dd7`. It adds a CoreMIDI device at `0x249a`. `SetupEndpoints` at `0x17a8` visits CoreMIDI sources and destinations and sets their refcons. These endpoints are CoreMIDI objects. |
| Client start | `L6MIDIDevInstance` connects to the service, opens its user client, registers the run loop, opens MIDI input, and opens output, at `0x14e3`, `0x14f7`, `0x1526`, `0x154e` and `0x156d`. `L6KIOMIDI` calls asynchronous selector 7 for input, scalar selector 4 for output, and selectors 3 and 5 to close the respective directions. |
| Client payload | `L6KIOMIDI::SendBytes` feeds individual MIDI bytes to `L6MidiRouteAndParse::Process` at `0x39d8`. It passes the parser's buffer and byte count to user-client selector 6 at `0x3a1b`. Kernel `SendMIDIBytes` at `0x164c` routes the payload through `L6KMIDIManager::Send`. The supported plug-in binary has no dependency on `L6TWX_u.dylib` and no direct USB interface-open call was identified. |
| Kernel interface | In `Line6Audio`, the `com_line6_audio` startup path saves its matched `IOUSBInterface` at `0x38f9`. At `0x3571`–`0x3584` it wraps that same provider and stores the wrapper at `this+0x100`. For PID `0x4650` the factory supplies alternate 1 from field `+0x18` (`0x2ff22`). MIDI setup obtains that wrapper at `0x11467` and calls `SelectTransferSetting(true)` at `0x1148c`. On first use the latter forwards the stored alternate at `0x1440d`–`0x1441c`. The Live plist's provider is interface 0. |
| Kernel pipes and initial I/O | `Setup` finds interrupt IN and OUT by type and direction at `0x114b7` and `0x114f6`. If IN is found it calls `ClearPipe(...,true)` at `0x114e0`. That helper constructs endpoint-recipient `CLEAR_FEATURE(ENDPOINT_HALT)` at `0x14001`–`0x14051`. Setup can start a read at `0x1152c` when a buffer and IN pipe are present. Successful reads feed the completed bytes to `L6KMIDIManager::Send` at `0x116d9` and requeue the read. |
| Framing | `WriteMIDI` accepts at most 256 bytes, copies them into its transmit context at `0x1176d` and has a conditional first-byte low-nibble mask at `0x11784`. The constructor clears that flag at `0x11e6b`. This routine contains no four-byte USB-MIDI event-packet encoder. Kernel routing before `WriteMIDI` and the physical split of long messages remain separate questions. |
| Vendor helper | `EnableProviderMIDIEP` at `0x11302` builds `40 67`, value `0x0101` for true or `0x0001` for false, index 0, length 0. MIDI setup dispatches the true case through vtable slot `+0x850` at `0x11540` (slot address `0xa8360`, target `0x11302`). The separate `0x0301` request in audio device setup is guarded by factory byte `+0x1e`. The constructor clears that byte and the Live PID branch leaves it clear. |

**Inference.** Applying the saved Live descriptors to the kernel pipe search gives interface 0 alt 1 interrupt IN `0x84` and OUT `0x03`, both with 16-byte maximum packets. The documented kernel MIDI path uses the matched interface 0. The reviewed CoreMIDI plug-in path has no evidence of claiming interface 1. Possible interface-1 activity elsewhere in the package remains **unknown**.

**Static fact.** The [Linux Variax driver path](linux-transport.md) instead selects interface 1 alt 1 with `0x86/0x05` and uses its own identity/activation sequence. The [original editor native backend](native-analysis.md) has a separate `BuildAndSendVariaxMidi` path. **Inference.** The app can investigate two routes offline for a user-space adapter: the Linux-style direct guitar exchange on interface 1 and the POD MIDI stream on interface 0 with the editor's application-layer bridge. The recovered macOS vendor startup runs on the POD side. Its `0x67` request shape differs from the Windows startup request and from the Linux interface-1 identity sequence. It must not be inherited as an interface-1 prerequisite from this evidence.

**Unknown.** Whether this package carries a successful Variax exchange on the CoreMIDI route for the Live, the complete mapping from native editor private messages to USB, per-message USB transfer segmentation, cleanup behavior on current macOS, and whether macOS allows a user-space process to claim each interface. **Inference — device risk.** The Intel driver's setup can select an alternate, clear an endpoint's halt, queue interrupt reads and send a vendor control request before an editor sends its first MIDI message.

## Audio kext

**Static fact.** The PODxt Live factory branch at `0x2ff04` supplies the XT profile and alternate 1. The shared `CreateEngine` routine selects `com_line6_driver_isoenginext` when its engine selector is 1 at `0x9eb1`–`0x9ed0`. The [existing audio dataflow trace](audio-capture-session.md) ties this selector to the exact Live personality. The audio and MIDI paths share the interface-0 provider.

| Stage | Static fact — 7.6.8 x86_64 | Inference or unknown |
| --- | --- | --- |
| Prepare | `PrepareEngine` dispatches to XT `SetupEngineCharacteristics` at `0x9077` (vtable slot `+0x978` → `0x79056`). It searches for isochronous pipes by direction at `0x90ff` and `0x9140`, retains them, and allocates transfer state. | **Inference.** On saved interface 0 alt 1 the only matching pair is playback OUT `0x01` and recording IN `0x82`. Their descriptor limits are 240 and 252 bytes, respectively, with `bInterval=1`. Alt 0 lists both with a zero packet size. |
| Format | `0x9dca0` and `0x9dca4` give one format and four rate records. At `0x9dce0` the format starts with two channels, `lpcm`, `sint` and raw 24/24 width bytes. `0x9dcc0` holds 44,100, 48,000, 88,200 and 96,000 Hz with zero fractional words. For the 24-width branch, pipe-side fields at `0x79121`–`0x79181` use two channels, width 24 and frame size 6. The standard-size pipe preparation at `0x79243`–`0x79295` uses OUT 234/240 and IN 252/252 byte arguments with a six-byte frame. Another branch uses 288/300 nominal values. The internal host-side callback copy uses an eight-byte stereo stride. | **Inference.** The six-byte pipe accounting is consistent with two 24-bit samples. The host-facing rates and buffer format can differ from the physical USB clock and samples. **Unknown.** Exact hardware clock negotiation, valid-bit alignment and byte order from this Mac trace. |
| Start and recycle | Core Audio's `performAudioEngineStart` reaches base `StartEngine` through slot `+0x878`. Its call at `0x9552` resolves to XT `OnStartEngine` at `0xeb98`, which resets counters and clears buffers. Base code queues enabled directions at `0x9654` and `0x9685`. `QueueFrameList` uses a frame-number source, builds a transfer and dispatches via the pipe vtable. Completion can queue the next frame list at `0x80ca`. | **Unknown.** Actual host scheduling, which directions a current host will start, and whether attach can trigger a stream through an OS client. An audio open can enqueue device traffic in both directions and affects playback/monitoring risk. |
| Controls | The adjacent MIDI service can select interface 0 alt 1 and issue the requests documented above during setup. A separate shared-XT user-client method, `VersionStatusCommand` at `0x13892`, builds `c0 67 11 00 00 00 03 00` on the control endpoint. The [USB firmware analysis](pod-usb-firmware.md) traces this as selector 6 of the shared-XT service, a different user client from MIDI selector 6. | **Unknown.** All device-specific or indirect control requests during audio preparation, power transitions, and automatic format changes. The version method's existence alone does not make it a stream-start request. |

**Static fact.** The [Linux POD audio definition](pod-usb-audio.md) uses the same interface and isochronous pair, two channels, six-byte packed little-endian frames and a declared rational rate of `78125/2`. Its startup path also has an explicit identity request and conditional serial read, documented under [Linux G1](hardware-gates/g1.md). **Inference.** The Mac advertised integer host rates and Linux rational PCM declaration describe different layers. Their difference is evidence against choosing a physical bus clock from the Mac UI rates. A similar endpoint map also gives no basis for copying Windows control writes to macOS.

## Adapters and gate equivalents

**Inference — Intel.** If legacy 7.6.8 support is verified for the target OS and machine, use CoreMIDI through the signed audio kext and MIDI plug-in for the POD MIDI route. Use the original application's `03 23` route as the candidate for reaching the guitar there. A user-space USB adapter is the other candidate when its required interface is available. The inspected kext binds interface 0 and may begin MIDI traffic before a client opens a CoreMIDI port.

**Inference — Apple Silicon.** Prefer a native user-space USB adapter, beginning with a descriptor check for configuration 1 and the two interface/alternate endpoint maps. Interface 1 alt 1 and `05/86` are the candidate for the direct Variax path from Linux. Interface 0 alt 1 and `03/84` are the candidate for POD MIDI. A usable adapter depends on macOS granting ownership and on establishing which startup requests, if any, each route actually requires. The observed Intel `0x0101` control request applies to the kernel MIDI setup on interface 0. Audio support is a separately gated path.

| Equivalent | Inference — Intel vendor driver | Inference — native user-space USB on Intel or Apple Silicon |
| --- | --- | --- |
| G1 — recognition | Read the existing I/O Registry device/service and CoreMIDI inventory. An already installed package may match and start its kext and publish MIDI/audio services on connect. Installing the legacy package would be separate system work involving a kext, MIDI bundle and host security policy. | Read cached registry identity and interface records through the OS. Leave interfaces unopened and alternates untouched. Existing OS drivers and applications can still act on connect. |
| G2 — identify the Variax | Open CoreMIDI client ports and associate the correct source/destination. Use a bounded bridge and identity exchange only after the route is approved. The bridge can change routing state. Close the client ports and apply the approved session cleanup. | Temporarily acquire interface 1 if it is available and permitted, select alternate 1, and use a bounded identity exchange on `05/86`. Selection and I/O change transient USB state. Restore the prior alternate where required by the approved procedure, release the interface and close the device handle. If a driver owns it, stop that attempt. |
| G3 — read current settings | Reuse the approved MIDI route for current Variax metadata and POD tone. Release the bridge and close MIDI resources as defined by the procedure. | Use separately acquired, verified interface routes for the current guitar and POD reads. Close both transport sessions and restore any alternate settings changed by the app. Verify that every app-originated request is within the read scope. |

**Unknown.** Legacy Intel OS loading and CoreMIDI availability, current host USB permissions and competing drivers, Apple Silicon interface exclusivity, on-wire framing for every MIDI route, exact original private Variax dispatch, and recovery if a session is interrupted. Proposed equivalents cover recognition, one identity operation and current settings. They require independent owner review before activation. The [Linux G2 record](hardware-gates/g2.md) and [G3 scope](hardware-gates.md) supply comparison evidence.
